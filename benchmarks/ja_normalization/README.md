# Japanese text-normalization benchmark

Measures what the TTS service's normalization layer does to Japanese request
text: `text_normalization.normalize("jp", ...)`, which wraps
[WeTextProcessing](https://github.com/wenet-e2e/WeTextProcessing)'s
`tn.japanese` WFST grammars.

Three adapters run over identical inputs so the comparison is before/after on
the thing that actually ships:

| adapter | what it is |
| --- | --- |
| `baseline` | what the service did before — text forwarded untouched |
| `library` | `tn.japanese.Normalizer` called directly |
| `normalized` | what ships: the wrapper, with tag masking, phone pre-rule, punctuation restoration and emoji stripping |

## Layout

| file | what it does |
| --- | --- |
| `ja_reading.py` | kanji-numeral reading rules, variant-tolerant canonicalization, leak detection, CER |
| `build_dataset.py` | builds both tracks into `data/` |
| `bench.py` | runs all three adapters, scores, prints the tables |
| `conformance.py` | runs WeTextProcessing's own test data through our wrapper |
| `../bench_core.py` | shared runner and scorer (also used by `vi_normalization`) |

## Dataset

**Track A — `data/gold.jsonl` (10,000 cases).** Japanese carrier sentences, each
containing one non-standard word whose accepted spoken form is known by
construction: 25 categories × 400 — cardinals (plain, comma-grouped, full-width
`１２３`), decimals, negatives, fractions, percentages, JPY and foreign money,
full and partial dates, times, ranges, mobile and landline phone numbers,
measures, counters (`3人`, `4部`, `5匹`), ordinals, maths, symbols, emoji, sport
scores, serial codes and multi-NSW sentences.

**Track B — `data/real.jsonl` (3,000 sentences).** Real Japanese Wikipedia
sentences containing NSWs, pulled through the HF datasets-server. No reference
exists, so these are scored on reference-free signals only: residual
unspeakable characters, crash rate and latency at realistic lengths.

## Scoring

Readings are generated by `ja_reading.py` from first principles rather than
taken from the library, so the benchmark measures the library instead of
echoing it. Conventions that are all correct Japanese are folded before
comparison — `〇`/`零`/`ゼロ`, a dropped leading `一` before `十/百/千`
(`一千万` == `千万`), and phone separators `の`/`ー`/`-`. Genuinely different
*structures* — a year as a cardinal (`二千二十三年`) vs as digits (`二〇二三年`),
a long digit string as a quantity vs digit-by-digit — are listed as alternative
accepted readings instead, because folding those would hide real errors.

`accuracy` is the share of cases where an accepted reading appears in the
output. `leak` is the share of outputs still containing a character a Japanese
TTS front-end cannot pronounce: digits (half or full width), maths/currency/unit
symbols, emoji. Japanese punctuation is prosody, not a leak; Latin letters are
not a leak either, since Japanese text legitimately contains them. `wer` is
really a character error rate — Japanese has no word boundaries.

## Conformance gate

`conformance.py` runs the 141 `input => expected` pairs that ship inside
WeTextProcessing (`tn/japanese/test/data/*.txt`) through our wrapper. This
answers a different question from the benchmark: not "is the library good
enough" but "are we driving it the way its authors intended". Any mismatch
means our configuration changed the library's documented behaviour.

**Result: 141/141 pairs match.**

## Wrapper rules, and why each exists

The wrapper is not a pass-through. Each rule was added because the benchmark
showed a measurable problem, and kept only because the benchmark showed it
helped:

- **Sentence terminators restored.** `tn.japanese` rewrites `。？！` to ASCII on
  *every* sentence, including ones with nothing to normalize — `full_to_half`
  does not gate it. Left alone, enabling normalization would alter the prosody
  of all Japanese traffic. Restoration is narrow: only a terminator directly
  after kana/kanji, plus a trailing one the caller actually wrote full-width,
  so `example.com` and decimal points are untouched.
- **Phone numbers pre-verbalized.** The library's maths rule beats its phone
  rule once the number sits inside a sentence: `番号は090-1234-5678です` came
  back as `〇九〇マイナス千二百三十四マイナス五千六百七十八` — the hyphens read as
  minus signs. This is the library's own documented example, and it fails in
  exactly the shape the service receives. A candidate must carry 10 or 11
  digits to be rewritten, which keeps dates like `08-08-2008` out of it.
  Measured effect: landline 41.2% → 100.0%, mobile 69.2% → 90.2%, with no
  category regressing.
- **Residual emoji stripped.** The library passes emoji straight through and no
  model has a pronunciation for them; soe-vinorm already drops them on the
  Vietnamese side, so this keeps the two endpoints consistent. Deliberately
  narrow — dropping a unit sign like `°` would silently change meaning, so
  those stay visible as a known gap instead.

## Reproduce

```bash
conda activate omnivoice-nlp
python build_dataset.py --per-category 400 --real 3000
python conformance.py
python bench.py
```

## End-to-end result — read this before trusting the front-end numbers

The front-end score says normalization takes Japanese from 0% to 88% correct.
The *audio* says something more complicated, and the audio is what matters.

Two live A/B tests against the running service (`../e2e_ab.py`,
`../ja_category_ab.py`), each sentence synthesized twice — once with
`normalize: false`, once normally — and every clip transcribed with Whisper
large-v3-turbo:

**500 real Wikipedia sentences**, character error rate against the correct
spoken form:

| | raw | normalized |
| --- | ---: | ---: |
| all 500 | 13.5% | 14.2% |
| the 461 that are genuinely Japanese | 9.9% | **10.5%** |

126 sentences improved, 188 got worse. (The other 39 are English bibliography
lines that Japanese Wikipedia articles carry in their reference lists — the
normalizer dutifully reads `1956` in an English citation as `千九百五十六`. Those
are a sampling artifact of the corpus, not of the normalizer, and excluding
them does not change the direction of the result.)

**140 gold sentences, 10 per category**, scored on the only question that
matters per category — did the listener hear the right thing?

| category | raw heard | normalized | |
| --- | ---: | ---: | --- |
| time (`3:40pm`) | 0% | **60%** | normalization essential |
| measure (`10km/h`) | 20% | **80%** | normalization essential |
| cardinal_grouped (`150,000`) | 20% | **50%** | helps |
| money_jpy | 50% | **70%** | helps |
| emoji, symbol | 100% | 100% | no difference |
| fullwidth_digits | 50% | 50% | no difference |
| date_full | 60% | 50% | hurts |
| phone_mobile | 50% | 30% | hurts |
| counter (`3人`), ordinal (`第3回`) | 100% | 70% | hurts |
| cardinal_small, percent | 100% | 60% | hurts |
| decimal | 90% | 30% | hurts |
| **overall** | **67%** | **63%** | |

### Why

The checkpoint already reads Arabic numerals in Japanese correctly — `7代目`,
`17世紀` and `4区` all come out right — and it *misreads* the kanji-numeral
forms the normalizer produces: `七代目` was heard as "ナチダイメ", `十七世紀` as
"住者正規". Japanese is written with Arabic numerals constantly, so digits are
in-distribution for this model and kanji numerals are comparatively rare.
Standard text normalization moves the text away from what the model knows.

Where the model genuinely cannot cope — a clock time like `3:40pm`, a compound
unit like `10km/h`, a comma-grouped `150,000` — normalization is the difference
between intelligible and not.

### The fix: a kana reading, not kanji numerals

Kanji numerals are the correct answer to the question WeTextProcessing is
designed to answer — canonical *written* Japanese, so TN and ITN stay
symmetric. They are the wrong answer for a TTS front-end, because the reading
is still ambiguous and the model has to resolve it.

A kana reading removes the ambiguity: there is nothing left to resolve. The
reading has to come from a morphological dictionary rather than a rewriter,
because Japanese number readings depend on the following counter and are
irregular (1本 いっぽん / 3本 さんぼん / 6本 ろっぽん; 1人 ひとり / 2人 ふたり /
3人 さんにん; 20日 はつか). `pyopenjtalk` (Open JTalk + unidic) supplies it.
WeTextProcessing's own `transliterate=True` flag does *not* — it is a static
6,791-entry loanword table (`.com` → ドットコム) with no number entries.

The two are complementary, and each fixes what the other gets wrong:

| input | pyopenjtalk alone | WeText alone | chained |
| --- | --- | --- | --- |
| `17世紀` | ジューナナセーキ ✓ | 十七世紀 ✗ | ✓ |
| `150,000円` | ヒャクゴジュー，ゼロゼロゼロエン ✗ | 十五万円 | ジューゴマンエン ✓ |
| `3:40pm` | サン：ヨンジューピーエム ✗ | 午後三時四十分 | ゴゴサンジヨンジュップン ✓ |
| `2023/11/14` | ニセンニジューサン／ジューイチ／… ✗ | 二千二十三年… | …ジューヨッカ ✓ |

So the shipped pipeline is **WeTextProcessing for structure, pyopenjtalk for
the reading**, applied furigana-style: only the fragments normalization
actually rewrote get a kana reading, and the rest of the sentence stays
ordinary Japanese. `OMNIVOICE_JA_KANA` selects `spans` (default), `full`
(whole utterance) or `off` (kanji numerals).

**144 gold sentences, 12 per category, four arms** — share heard correctly:

| category | raw | kanji | **spans** | full |
| --- | ---: | ---: | ---: | ---: |
| cardinal_small | 92% | 58% | **92%** | 50% |
| cardinal_grouped | 8% | 75% | 58% | 58% |
| date_full | 33% | 17% | **67%** | 42% |
| time | 0% | **100%** | 75% | 75% |
| money_jpy | 42% | **100%** | 92% | 67% |
| measure | 50% | 83% | **100%** | 75% |
| counter | 92% | 42% | 75% | 67% |
| percent | 92% | 83% | **100%** | 92% |
| ordinal | **100%** | 67% | 92% | 67% |
| phone_mobile | **58%** | 0% | 50% | 25% |
| decimal | 67% | 50% | **83%** | 42% |
| fullwidth_digits | 42% | 75% | 92% | **100%** |
| **OVERALL** | **56%** | **62%** | **81%** | **63%** |

Per-category cells move ±8pp per sentence at n=12, so read the overall row.
It came out at exactly 81% on two independent synthesis runs.

Phone numbers are the one place where doing nothing wins: the model reads
`090-1234-5678` better than any spelled-out form, so under a kana reading the
phone span is protected from the grammar rather than rewritten.

### Why the 500-sentence CER looks flat

Re-running the 500 Wikipedia sentences with the kana arm:

| | raw | kanji | kana |
| --- | ---: | ---: | ---: |
| all 500, mean CER | 13.5% | 14.2% | **13.2%** |
| genuinely Japanese, mean | **9.9%** | 10.5% | 10.2% |
| genuinely Japanese, median | **7.1%** | 7.4% | 7.3% |

Kana erases the kanji regression but does not beat raw here — and that is a
property of the measurement, not of the fix. Normalization rewrites a median
of **6%** of a prose sentence, and 43% of these sentences have under 5%
rewritten. Whole-sentence CER is therefore dominated by the ~94% that never
changed, and model/ASR variance on that part swamps the effect. The gold set
puts exactly one NSW in each sentence and scores that NSW, which is why it can
resolve a 25-point difference the CER cannot.

Use the gold numbers to choose the mode; use the CER to confirm the mode does
no harm to ordinary prose. Both say ship `spans`.

### Front-end numbers for the shipped pipeline

10,000 gold cases, scored in pronunciation space — both sides mapped to their
reading before comparison, because the pipeline emits kana for rewritten
fragments and kanji elsewhere, and a written-form comparison would score a
correct kana reading as wrong:

| | baseline (raw) | kanji | **shipped (furigana)** |
| --- | ---: | ---: | ---: |
| accuracy | 42.1% | 84.5% | 83.7% |
| error rate vs gold | 12.8% | 5.7% | **2.5%** |
| unspeakable-char leak | 100% | 7.8% | 12.3% |

Three things to read carefully here:

- **The baseline is not zero.** A reading engine can pronounce bare digits, so
  in pronunciation space raw text already scores 42.1%. That measures what a
  G2P engine would do, not what the TTS model does — the model is not a G2P
  engine, which is the entire point of the audio test above.
- **kanji and furigana score about the same on accuracy** (84.5% vs 83.7%):
  both encode a correct reading. What separates them is whether the model can
  *act* on it, and only the audio test sees that (62% vs 81%). The error rate
  does pick up the difference — 5.7% vs 2.5% — because furigana pins the
  pronunciation exactly rather than leaving it to be inferred.
- **The higher leak is deliberate.** Phone numbers stay as written digits
  (+4pp) because the model reads them better that way; the remainder is the
  symbol category, which neither pipeline expands.

### Cost

5.9 ms mean, 11.3 ms p95 per sentence over 3,000 real sentences with a cold
cache — against roughly 1.2 s of synthesis.
